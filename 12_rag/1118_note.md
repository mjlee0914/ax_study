### [ReRanking 기법 - 재순위 산출]

```
질문 - 맥락 문서 => 의미 관련성 수치
```

- 관련성 수치를 통해 랭킹을 바꾼다

#### Bi-Encoder 구조

```
질문 → 임베딩 ┐
              ├─ 코사인 유사도 등 → 유사도 점수
문서 → 임베딩 ┘
```

- 질문과 문서를 **따로** 벡터로 바꾼 뒤 두 벡터를 비교한다
- 문서 임베딩은 미리 계산해서 VectorDB에 저장해 둘 수 있다 → 그래서 빠르고 캐싱이 된다
- 역할: **1차 검색** (retriever)

##### Bi-Encoder는 임베딩까지만

- Bi-Encoder **모델이 하는 일은 임베딩(벡터) 만들기까지**
- 유사도 점수는 모델 밖에서 간단한 수학 계산(코사인 유사도)으로 구한다

```
[모델이 하는 일]                 [모델 밖에서 하는 일]
질문 → 모델 → 벡터 ┐
                   ├→ 코사인 유사도 계산 → 점수
문서 → 모델 → 벡터 ┘   (VectorDB가 계산, 모델 실행 없음)
```

|                    | Bi-Encoder                       | Cross-Encoder |
| ------------------ | -------------------------------- | ------------- |
| 모델이 내놓는 것   | **벡터** (예: 숫자 768개, 1536개) | **점수 1개**  |
| 점수는 누가 계산?  | 모델 밖 (코사인 유사도 계산)     | 모델이 직접   |
| 점수 범위          | -1 ~ 1 (코사인 유사도)           | 0 ~ 1 (sigmoid) |

- 빠른 이유: 질문만 모델에 1번 넣고, 나머지는 벡터끼리 곱하고 더하는 가벼운 계산
- LangChain에서는
  - `OpenAIEmbeddings`, `HuggingFaceEmbeddings` 같은 **임베딩 모델 = Bi-Encoder** → 벡터만 만든다
  - 유사도 계산과 검색은 **VectorStore**(Chroma, PGVector 등)가 한다 → `similarity_search()`
- ⚠️ 점수 범위가 달라서 Bi-Encoder 점수와 Cross-Encoder 점수를 숫자로 직접 비교하면 안 된다

##### Bi-Encoder의 맥락 파악 능력

- ✅ **텍스트 하나 안의 맥락은 잘 이해한다**
  - 내부가 Transformer라서 문장 안의 단어들이 서로를 참고한다
  - "사과를 먹었다"와 "사과를 했다"의 사과를 다르게 표현한다
  - "환불 방법"과 "돈 돌려받는 법"처럼 단어가 달라도 의미가 비슷하면 찾아낸다 → 키워드 검색(BM25)보다 나은 점
- ❌ **질문과 문서 사이의 맥락은 약하다**
  - 문서를 벡터로 만들 때는 어떤 질문이 들어올지 모른다
  - 정보 압축 손실: 긴 문서 전체를 벡터 하나에 담아서 세부 정보가 흐려진다
  - 주제만 비슷하면 점수가 높게 나와서 세밀한 차이를 놓친다
    - 부정: "환불이 **되는** 경우" vs "환불이 **안 되는** 경우"
    - 관계 방향: "A가 B를 이겼다" vs "B가 A를 이겼다"
    - 조건: "2023년 정책" vs "2024년 정책"

> 비유: Bi-Encoder는 책마다 **한 줄 요약**만 보고 질문과 비교한다. Cross-Encoder는 질문을 손에 든 채로 **책 본문을 직접 읽는다**.

#### Cross-Encoder

```
질문 + 문서 (한 쌍)
      ↓
트랜스포머 인코더 모델
      ↓
이진 분류 (0 ~ 1)
```

- 질문과 문서를 **한 쌍으로 묶어서** 모델에 같이 넣는다
- 모델 안에서 질문과 문서의 단어들이 서로를 직접 참고한다 → **정확도가 높다**
- 문서를 미리 계산해 둘 수 없고 쌍마다 매번 계산한다 → **느리다**
- 역할: 1차 검색으로 줄인 후보만 **2차 재정렬** (리랭킹)
- 실습 예시: `HuggingFaceCrossEncoder(model_name="Dongjin-kr/ko-reranker")`

##### Cross-Encoder는 이진 분류?

- **학습할 때**: (질문, 문서) 쌍마다 "관련 있음(1) / 관련 없음(0)" 정답을 주고 학습한다 → 이진 분류
- **사용할 때**: 0 / 1로 딱 자르지 않고 **0 ~ 1 사이의 관련성 점수**를 그대로 쓴다
  - 1에 가까울수록 관련 있음
  - 이 점수로 문서를 정렬해서 `top_n=2`처럼 상위 몇 개만 남긴다
- `ko-reranker`의 `config.json`에서 확인한 것
  - `"architectures": ["XLMRobertaForSequenceClassification"]` → 분류 모델 구조
  - `"id2label": {"0": "LABEL_0"}` → 출력이 **1개** (관련성 점수 하나)

> 비유: 채점은 정답/오답(이진)으로 하지만, 결과로 나오는 건 합격/불합격이 아니라 **확신도 점수**다. 그 점수로 줄을 세운다.

##### 직접 실행해서 점수 확인 (ko-reranker)

질문: **"환불은 어떻게 받나요?"**

| 점수     | 문서                                                            |
| -------- | --------------------------------------------------------------- |
| 0.706137 | 구매 후 7일 이내에 고객센터로 요청하면 환불을 받을 수 있습니다. |
| 0.000374 | 환불이 불가능한 상품 목록입니다.                                |
| 0.000054 | 오늘 서울의 날씨는 맑고 기온은 20도입니다.                      |

- 점수가 0 ~ 1 사이로 나온다 → sentence-transformers가 출력에 **sigmoid를 자동 적용** (`activation: Sigmoid()`)
- "환불이 **불가능한**" 문서는 "환불"이라는 단어가 들어 있는데도 점수가 매우 낮다
  → 질문과 문서를 같이 읽어서 **부정까지 구분**한다 (Bi-Encoder가 약한 부분)

##### Sigmoid란?

- 아무 숫자나 **0 ~ 1 사이로 눌러 주는 함수**

$$\sigma(x) = \frac{1}{1 + e^{-x}}$$

- 모델이 바로 내놓는 값(**logit**)은 범위가 정해져 있지 않다 (예: -9.8, 3.2) → 그대로는 해석하기 어렵다
- sigmoid를 거치면 확률처럼 읽을 수 있다

| logit (모델 원래 출력) | sigmoid 결과 | 의미      |
| ---------------------- | ------------ | --------- |
| 큰 음수 (예: -10)      | 0에 가까움   | 관련 없음 |
| 0                      | 0.5          | 반반      |
| 큰 양수 (예: +10)      | 1에 가까움   | 관련 있음 |

- 모양: 가운데는 가파르고 양 끝은 평평한 **S자 곡선**
- 실습 결과에 대입 (점수에서 거꾸로 계산한 값)
  - 0.706 → logit 약 +0.9 (관련 있는 편)
  - 0.000054 → logit 약 -9.8 (확실히 무관)
- 큰 값은 큰 값대로, 작은 값은 작은 값대로 유지된다 → **순위는 sigmoid 전과 똑같다**. 점수를 보기 좋게 바꿔 줄 뿐이다

> 비유: 아무리 세게 밀어도 0과 1 사이에서만 움직이는 볼륨 다이얼

##### Cross-Encoder의 맥락 파악 능력과 속도

- ✅ **맥락 파악 능력이 좋다**: 질문과 문서를 한 번에 넣어서, 모델 안에서 질문 단어와 문서 단어가 서로를 직접 참고한다
- ❌ **연산량이 많아서 느리다**
  - 문서를 미리 계산해 둘 수 없다 → 질문이 들어올 때마다 계산을 처음부터 다시 한다
  - 문서 N개를 비교하려면 모델을 **N번** 실행해야 한다
    - Bi-Encoder: 질문 임베딩 **1번** + 미리 저장한 벡터와 비교 (계산이 가벼움)
    - Cross-Encoder: (질문, 문서1), (질문, 문서2), … **N번** 전부 모델 실행
  - 질문과 문서를 붙이면 입력이 길어진다 → Transformer는 입력이 길수록 계산량이 크게 늘어난다
- 그래서 문서 전체에는 쓰지 못하고, **1차 검색으로 줄인 소수의 후보에만** 쓴다

##### Cross-Encoder는 2차에서만 쓸까?

- 기술적으로는 1차에도 쓸 수 있다. 하지만 **문서가 아주 적을 때만** 현실적이다
  - 1차에 쓰려면 질문과 **모든 문서**를 하나씩 짝지어 모델에 넣어야 한다

| 전체 문서 수 | Cross-Encoder를 1차에 쓰면 | 현실성                |
| ------------ | -------------------------- | --------------------- |
| 20 ~ 50개    | 모델 20 ~ 50번 실행        | ✅ 가능 (몇 초 정도)  |
| 1만 개       | 모델 1만 번 실행           | ❌ 질문 하나에 몇 분  |
| 100만 개     | 모델 100만 번 실행         | ❌ 불가능             |

(시간은 대략적인 감이고 직접 재 보지는 않음)

- 1차와 2차를 나누는 기준은 **후보 수**다
  - 1차: 후보가 많다 → 빠른 방법 (Bi-Encoder, BM25)
  - 2차: 후보가 적다 → 느려도 정확한 방법 (Cross-Encoder)
- Cross-Encoder가 2차에 있는 건 규칙이라서가 아니라, **느려서 후보가 줄어든 뒤에야 쓸 수 있기 때문**이다
- 단계를 더 나누기도 한다: 1차 BM25 → 2차 Bi-Encoder → 3차 Cross-Encoder
- 참고: 속도와 정확도 사이를 노리는 중간 방식으로 **ColBERT** (late interaction)도 있다

##### 실습 코드 (05_04.ipynb)

```python
# 1차: BM25로 상위 3개 후보
base_retriever = BM25Retriever.from_documents(documents=raw_documents, preprocess_func=custom_tokenizer)
base_retriever.k = 3

# 2차: Cross-Encoder로 재정렬 후 상위 2개만 남김
reranker = CrossEncoderReranker(model=cross_encoder_model, top_n=2)

rerank_retriever = ContextualCompressionRetriever(
    base_compressor=reranker,        # 2차
    base_retriever=base_retriever    # 1차
)
```

- 1차의 `k`가 Cross-Encoder 실행 횟수를 정한다 → `k=3`이면 Cross-Encoder는 3번만 실행된다
- 이 실습의 1차는 Bi-Encoder가 아니라 **BM25(키워드 검색)** 다 → 1차에는 빠른 방법이면 무엇이든 쓸 수 있다

### 비교

|        | Bi-Encoder            | Cross-Encoder      |
| ------ | --------------------- | ------------------ |
| 입력   | 질문, 문서 따로       | (질문, 문서) 한 쌍 |
| 속도   | 빠름 (미리 계산 가능) | 느림 (매번 계산)   |
| 정확도 | 상대적으로 낮음       | 높음               |
| 역할   | 1차 검색              | 2차 재정렬         |

> 비유: Bi-Encoder = 의미가 비슷한 후보를 빠르게 거르는 서류 심사 (키워드로 거르는 건 BM25), Cross-Encoder = 남은 후보를 한 명씩 보는 면접

### BM25 vs Bi-Encoder

- 한 줄 요약: BM25는 **단어가 겹치는지**, Bi-Encoder는 **뜻이 비슷한지**를 본다

#### BM25: 키워드 검색 (모델 없음)

- 질문 단어가 문서에 **얼마나 자주, 얼마나 특별하게** 나오는지로 점수를 매긴다
  - **TF (단어 빈도)**: 질문 단어가 문서에 많이 나올수록 점수 ↑
  - **IDF (희귀도)**: 흔한 말("은/는")보다 드문 단어("환불", "PGVector")가 일치할 때 점수를 더 준다
  - **문서 길이 보정**: 긴 문서가 단어 수만 많아서 유리해지지 않게 조정한다
- 딥러닝 모델 없이 계산 공식만으로 동작한다

#### Bi-Encoder: 의미 검색 (모델 사용)

- 질문과 문서를 모델로 **의미 벡터**로 바꾸고, 벡터끼리 얼마나 가까운지 비교한다

#### 비교

|                                       | BM25                      | Bi-Encoder                     |
| ------------------------------------- | ------------------------- | ------------------------------ |
| 기준                                  | **단어 일치**             | **의미 유사**                  |
| "환불 방법" vs "돈 돌려받는 법"       | ❌ 못 찾음 (겹치는 단어 없음) | ✅ 찾음                     |
| 고유명사, 코드, 숫자 (`ERR-4012` 등)  | ✅ 정확히 찾음            | ⚠️ 놓칠 수 있음                |
| 모델 / 학습                           | 필요 없음                 | 임베딩 모델 필요               |
| 비용                                  | 거의 없음                 | 임베딩 계산 비용 (API면 유료)  |
| 저장 방식                             | 단어 → 문서 목록 (sparse) | 숫자 벡터 (dense)              |
| 한국어                                | **토크나이저가 중요**     | 모델이 알아서 처리             |

#### 한국어와 토크나이저

- BM25는 단어 단위로 비교한다 → "환불은", "환불을", "환불이"를 그대로 두면 **서로 다른 단어**로 본다
- 형태소 분석기(예: `kiwipiepy`)로 "환불"만 떼어 내야 제대로 일치한다
- 05_04 실습의 `custom_tokenizer`는 `text.split()`, 즉 **띄어쓰기로만 자른다** → 조사가 붙은 채로 비교된다 (형태소 분석은 안 함)

> 비유: BM25 = 책 뒤의 **색인(찾아보기)** (정확한 단어는 잘 찾지만 다른 표현은 못 찾음), Bi-Encoder = **내용을 이해하는 사서** (표현이 달라도 찾지만 정확한 모델명이나 코드는 헷갈릴 수 있음)

#### 하이브리드 검색

- 두 방식은 약한 부분이 서로 반대다 → 둘을 합쳐서 쓴다
- LangChain: `EnsembleRetriever`로 BM25와 벡터 검색 결과를 합친다

### [평가 지표]

> 검색(retrieval) 결과가 좋은지 평가하는 지표 (RAGAS 같은 평가 도구에서 사용)

#### 1. Context Precision (문맥 정밀도)

- **가져온 문서 중 쓸모 있는 게 얼마나 되는지 + 쓸모 있는 문서가 위쪽에 있는지**
- 예: 검색 결과 5개 중 관련 있는 게 4개 → 높음, 1개 → 낮음
- RAGAS에서는 **순위도 반영**한다: 관련 문서가 1~2등이면 점수 ↑, 4~5등에 밀려 있으면 점수 ↓
- 질문: "가져온 것 중에 **쓰레기가 적은가?**"

#### 2. Context Recall (문맥 재현율)

- **답하는 데 필요한 정보를 빠짐없이 가져왔는지**
- 정답(reference)을 문장 단위로 나눈 다음, 각 문장이 가져온 문서로 뒷받침되는지 확인한다
- 예: 필요한 정보 3개 중 2개만 문서에 있음 → 2/3 ≈ 0.67
- 질문: "필요한 걸 **빠뜨리지 않았는가?**"

> 비유: 그물로 물고기 잡기 🎣
> - Precision = 잡아 올린 것 중 물고기 비율 (쓰레기가 섞이면 ↓)
> - Recall = 바다에 있던 목표 물고기 중 실제로 잡은 비율 (놓치면 ↓)
> - 그물을 넓게 던지면 Recall ↑, Precision ↓ → 보통 **trade-off** 관계

#### 리랭킹과 연결

| 단계                                | 주로 올리는 지표                             |
| ----------------------------------- | -------------------------------------------- |
| 1차 검색 `k`를 크게 (예: 3 → 20)    | **Recall** ↑ (필요한 문서를 놓칠 확률 ↓)     |
| 2차 Cross-Encoder 리랭킹 + `top_n`  | **Precision** ↑ (관련 문서를 위로, 나머지 자름) |

- 리랭킹 파이프라인 = 1차에서 **넓게 잡아 Recall 확보** → 2차에서 **추려서 Precision 확보**

#### 3. F1 Score (성능 지표)

- **Precision과 Recall을 숫자 하나로 합친 점수**
- 필요한 이유: 둘은 trade-off라서 하나만 보면 어떤 방법이 나은지 판단하기 어렵다

$$F1 = \frac{2 \times Precision \times Recall}{Precision + Recall}$$

- 그냥 평균(산술평균)이 아니라 **조화평균**을 쓴다

|     | Precision | Recall | 산술평균 | **F1 (조화평균)** |
| --- | --------- | ------ | -------- | ----------------- |
| A   | 1.0       | 0.0    | 0.5      | **0.0**           |
| B   | 0.9       | 0.3    | 0.6      | **0.45**          |
| C   | 0.6       | 0.6    | 0.6      | **0.6**           |

- A: 하나도 못 찾았는데 산술평균은 0.5 → 너무 후하다
- 조화평균은 **둘 중 낮은 쪽에 끌려간다** → 한쪽만 높은 꼼수가 안 통한다
- B와 C는 산술평균이 같지만, F1은 **둘 다 고르게 높은 C**를 더 좋게 평가한다
- 계산 예시 (B): 2 × 0.9 × 0.3 / (0.9 + 0.3) = 0.54 / 1.2 = **0.45**
- 범위: 0 ~ 1 (1 = Precision, Recall 둘 다 완벽)
- 참고: RAG에서는 Context Precision과 Context Recall을 따로 보는 경우가 많고, F1은 분류 모델 평가에서 특히 자주 쓴다

> 비유: 팀 과제 점수를 **가장 약한 팀원 쪽으로** 맞추는 방식. 둘 다 잘해야 높은 점수가 나온다.

#### 정밀도(Context Precision)가 낮을 때 해결 방법

- 정밀도가 낮다 = **쓸모없는 문서가 많이 섞였거나, 좋은 문서가 아래로 밀렸다**

##### 먼저 원인 확인

- 점수가 낮은 질문의 **검색 결과를 직접 출력**해 본다
  - 관련 없는 문서가 **많이** 섞였나? → 개수나 필터 문제
  - 관련 문서는 있는데 **순위가 낮나?** → 순위 문제
  - 문서 하나 안에 **관련 내용과 무관한 내용이 섞여** 있나? → 청킹 문제

##### 해결 방법

| 원인                          | 해결 방법                                 | LangChain 예시                                                   |
| ----------------------------- | ----------------------------------------- | ---------------------------------------------------------------- |
| 좋은 문서가 아래로 밀림       | **리랭킹**                                | `CrossEncoderReranker` + `ContextualCompressionRetriever`        |
| 너무 많이 가져옴              | **`k` / `top_n` 줄이기**                  | `search_kwargs={"k": 3}`                                         |
| 점수 낮은 문서까지 들어옴     | **유사도 기준점(threshold)으로 자르기**   | `search_type="similarity_score_threshold"`, `EmbeddingsFilter`   |
| 문서 안에 잡음이 많음         | **청크 크기 줄이기 / 의미 단위로 자르기** | `chunk_size` 조정, `SemanticChunker`                             |
| 같은 내용이 중복으로 들어옴   | **중복 제거**                             | `EmbeddingsRedundantFilter`                                      |
| 엉뚱한 카테고리 문서가 들어옴 | **메타데이터 필터** (날짜, 부서 등)       | `search_kwargs={"filter": {...}}`                                |
| 의미를 잘못 잡음              | **임베딩 모델 바꾸기** (한국어에 강한 모델) |                                                                |
| LLM으로 직접 골라내기         | **LLM 필터 / 추출** (정확하지만 느리고 비쌈) | `LLMChainFilter`, `LLMChainExtractor`                         |

##### ⚠️ 주의: Recall도 같이 본다

- 대부분의 방법은 결국 **"덜 가져오기"** → 너무 세게 자르면 필요한 문서도 빠져서 **Recall ↓**
- 정석:
  1. 1차는 넉넉하게 가져와서 **Recall 확보** (`k` 크게)
  2. 2차 리랭킹으로 추려서 **Precision 확보** (`top_n` 작게)
- 고친 뒤에는 Precision과 Recall을 **둘 다** 다시 재서 비교한다 (F1 활용)

> 비유: 그물에 쓰레기가 많이 걸렸을 때 그물을 작게 만들면(`k` 줄이기) 물고기도 덜 잡힌다. 그물은 크게 던지고 **배 위에서 골라내는 것**(리랭킹)이 더 좋다.

#### 재현율(Context Recall)이 낮을 때 해결 방법

- 재현율이 낮다 = **답에 필요한 정보를 검색이 놓쳤다**

##### 먼저 원인 확인

- 점수가 낮은 질문에서 **정답에 필요한 문장을 원본 문서에서 직접 찾아본다**
  - 그 문장이 **VectorDB에 들어가 있긴 한가?** → 데이터 적재(로딩, 파싱) 문제
  - 들어가 있는데 **후보 `k`개 안에 못 들어왔나?** → 검색 범위나 표현 문제
  - 정보가 **여러 청크로 쪼개져서** 일부만 들어왔나? → 청킹 문제

##### 해결 방법

| 원인                              | 해결 방법                                    | LangChain 예시                 |
| --------------------------------- | -------------------------------------------- | ------------------------------ |
| 아예 DB에 없음                    | **문서 로딩, 파싱 점검** (표, PDF 깨짐 등)   | 로더 결과를 `print`로 확인     |
| 후보를 너무 적게 가져옴           | **1차 `k` 늘리기**                           | `search_kwargs={"k": 20}`      |
| 질문과 문서의 표현이 다름         | **질문 다시 쓰기 / 여러 버전으로 검색**      | `MultiQueryRetriever`          |
|                                   | **가상 답변을 만들어 그걸로 검색** (HyDE)    |                                |
| 고유명사, 코드를 의미 검색이 놓침 | **하이브리드 검색** (BM25 + 벡터)            | `EnsembleRetriever`            |
| 정보가 청크 경계에서 잘림         | **청크 크기, overlap 늘리기**                | `chunk_size`, `chunk_overlap`  |
|                                   | **작게 검색하고 크게 돌려주기**              | `ParentDocumentRetriever`      |
| 질문 하나에 정보가 여러 개 필요   | **질문 쪼개기** (하위 질문마다 검색)         |                                |
| 필터가 너무 빡빡함                | **threshold, 메타데이터 필터 완화**          |                                |
| 의미를 잘못 잡음                  | **임베딩 모델 바꾸기** (한국어에 강한 모델)  |                                |

##### ⚠️ 주의

- 대부분 **"더 많이, 더 넓게 가져오기"** → 쓰레기도 늘어서 **Precision ↓**
- 정석: Recall 개선 방법으로 **1차를 넓게** → 2차 리랭킹으로 **다시 추려서** Precision 유지
- 정리: **Recall 개선은 주로 1차 검색의 일, Precision 개선은 주로 2차의 일**
- 정답(reference)도 의심해 본다: 정답 자체가 문서에 없는 내용을 포함하면 검색을 잘해도 점수가 낮다 → 평가 데이터도 점검

> 비유: 그물을 **더 크게**(`k` ↑), **여러 곳에** 던지기(MultiQuery), **다른 종류의 그물**도 같이 쓰기(하이브리드), 처음부터 **물고기가 바다에 있는지** 확인하기(데이터 적재 점검)

### [생성 품질 지표]

> 검색된 context를 바탕으로 LLM이 만든 **응답**이 좋은지 평가하는 지표

#### 1. 신뢰도 (Faithfulness)

$$Faithfulness = \frac{\text{context로 입증 가능한 응답 문장(주장) 수}}{\text{응답의 전체 문장(주장) 수}}$$

- 개수가 아니라 **비율**이다
- 계산 순서
  1. **응답을 주장 단위로 쪼갠다**
     - 응답: "Python은 간결한 문법을 지닌 언어로, 1991년 귀도 반 로섬이 발표했다."
     - ① Python은 간결한 문법을 지닌 언어다
     - ② Python은 1991년 귀도 반 로섬이 발표했다
  2. **주장마다 context(검색된 문서)에서 뒷받침되는지 확인**한다
  3. **비율을 계산**한다

| context에 있는 내용 | ①  | ②  | Faithfulness   |
| ------------------- | -- | -- | -------------- |
| 둘 다 있음          | ✅ | ✅ | 2/2 = **1.0**  |
| ①만 있음            | ✅ | ❌ | 1/2 = **0.5**  |

- 헷갈리기 쉬운 점
  - 기준은 **응답의 문장**이다 (context의 문장 수가 아님)
  - **실제로 맞는 말이어도 context에 없으면 ❌** → "사실인가?"가 아니라 **"검색된 문서에 근거했는가?"**를 본다
  - 목적: LLM이 문서를 무시하고 지어낸 답(**hallucination**)을 잡아내기

| 지표           | 무엇을 쪼개나              | 무엇과 비교하나 | 평가 대상 |
| -------------- | -------------------------- | --------------- | --------- |
| Context Recall | **정답(reference)** 문장   | context         | 검색 품질 |
| Faithfulness   | **LLM 응답** 문장          | context         | 생성 품질 |

> 비유: 리포트에서 **문장마다 각주(출처)가 달려 있는지** 검사하는 것. 맞는 말이어도 참고문헌에 없으면 감점.

#### 2. 답변 관련성 (Answer Relevancy)

- **응답이 질문에 맞는 답을 했는지** 보는 지표
- 비교 대상: **질문 ↔ 답변** (context는 안 본다)

```
질문 ┐
     ├─ 얼마나 관련 있나? → 점수
답변 ┘
```

- 판단 방법 두 가지 (오늘 배운 두 인코더와 연결)

| 방법                              | 사용하는 인코더   | 특징                              |
| --------------------------------- | ----------------- | --------------------------------- |
| ① **임베딩 거리**로 판단          | **Bi-Encoder**    | 질문, 답변을 따로 벡터로 → 코사인 유사도. 빠름 |
| ② **트랜스포머 인코더**로 판단    | **Cross-Encoder** | 질문 + 답변을 한 쌍으로 모델에 넣음. 정확함 |

- 점수가 낮아지는 경우
  - 질문과 상관없는 말을 함 (예: "환불 방법?" → 회사 소개만 늘어놓음)
  - 질문의 일부에만 답함 (빠진 부분이 있음)
  - 쓸데없는 말이 너무 많음
- ⚠️ 이 지표는 **답이 사실인지, 문서에 근거했는지는 안 본다** → 그건 Faithfulness의 일
  - 질문에 딱 맞게 답했지만 지어낸 내용이면: Answer Relevancy ↑, Faithfulness ↓
- 참고: RAGAS는 답변을 보고 LLM이 "이 답이 나올 법한 질문"을 거꾸로 여러 개 만든 다음, 원래 질문과 **임베딩 유사도**(①번 방식)로 비교한다

| 지표             | 무엇과 무엇을 비교하나 | 확인하는 것                      |
| ---------------- | ---------------------- | -------------------------------- |
| Faithfulness     | 답변 ↔ context         | 문서에 **근거**했는가? (hallucination) |
| Answer Relevancy | 답변 ↔ 질문            | 질문에 **맞는** 답인가? (동문서답) |

> 비유: Faithfulness = 문장마다 **출처가 있는지** 검사, Answer Relevancy = **동문서답 안 했는지** 검사

### context = source?

- 거의 같은 뜻이지만, 정확히는 **검색돼서 LLM에게 전달된 문서 조각**

| 말                         | 범위                                                       |
| -------------------------- | ---------------------------------------------------------- |
| 원본 문서 (source / corpus) | VectorDB에 저장된 **전체** 문서                            |
| **context**                | 그중 이번 질문에 **검색돼서 LLM 프롬프트에 들어간** 청크 몇 개 |

```
05_04 실습: 전체 문서(source) → BM25로 3개 → 리랭커로 2개 → 이 2개가 context
```

- 중요한 이유: Faithfulness는 **context 기준**으로 채점한다
  - 원본 문서 어딘가에 있어도 **검색에서 빠져서 context에 없으면** ❌
  - 그래서 Python 예시의 ②가 실제 사실이어도 context에 없으면 점수를 못 받는다

> 비유: source = **도서관 전체**, context = 이번 리포트를 위해 **대출해 온 책 몇 권**. 각주는 대출해 온 책 안에서만 달 수 있다.

### 평가 지표 전체 정리

- RAGAS 데이터 하나의 구성 (괄호 안은 최신 버전 컬럼 이름, 버전마다 다를 수 있음)

| 항목                                | 뜻                   |
| ----------------------------------- | -------------------- |
| question (`user_input`)             | 사용자 질문          |
| **contexts** (`retrieved_contexts`) | 검색된 문서 조각들   |
| answer (`response`)                 | LLM 응답             |
| ground truth (`reference`)          | 사람이 만든 정답     |

- 지표마다 **어떤 두 가지를 비교하는지**로 구분된다

| 지표              | 비교하는 것                       | 평가 대상 |
| ----------------- | --------------------------------- | --------- |
| Context Precision | question ↔ contexts (+ reference) | 검색 품질 |
| Context Recall    | reference ↔ contexts              | 검색 품질 |
| Faithfulness      | answer ↔ contexts                 | 생성 품질 |
| Answer Relevancy  | answer ↔ question                 | 생성 품질 |

### [LLM이 대화를 기억하는 방법]

- 핵심: **LLM은 사실 기억을 못 한다 (stateless)**
  - API는 요청 하나하나를 **처음 보는 것처럼** 처리한다
  - 이전 대화가 모델 안에 저장되지 않는다
- 그럼 어떻게? → **매번 프롬프트에 지난 대화를 통째로 붙여서** 보낸다

```
┌──────────────────────────┐
│ (시스템 지시문)           │
│                          │
│ [지난 대화 내용]          │
│   Human: 내 이름은 명지야 │
│   AI: 안녕하세요 명지님!  │
│   Human: 내 이름이 뭐지?  │ ← 이번 질문
└──────────────────────────┘
```

- 모델은 프롬프트에 적힌 지난 대화를 **읽고** 답한다 (기억해서 답하는 게 아님)

> 비유: **기억상실증이 있는 상담사**. 매번 기억을 잃지만, 상담할 때마다 지금까지의 **상담 일지를 처음부터 읽고** 대답한다.

#### 문제점과 관리 방법

- 대화가 길어질수록 프롬프트가 커진다
  - **context window(입력 길이 제한)**를 넘을 수 있다
  - 토큰이 늘어서 **비용 ↑, 속도 ↓**

| 방법       | 설명                                         |
| ---------- | -------------------------------------------- |
| 전부 저장  | 대화 전체를 붙인다 (짧은 대화에 적합)        |
| 최근 N개만 | 오래된 대화는 버린다 (sliding window)        |
| 요약       | 오래된 대화를 LLM으로 요약해서 짧게 붙인다   |

- RAG와 같은 원리: "[지난 대화 내용]" 자리 = RAG에서 검색 문서(context)를 끼워 넣던 자리
  → 둘 다 **모델이 모르는 정보를 프롬프트에 넣어 주는 것**
- LangChain 구체적인 클래스는 버전마다 많이 바뀜 → 실습 코드 나오면 정리
